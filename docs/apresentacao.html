1. Visão Geral Introdução

Abertura da apresentação — o que é o projeto, stack, entidades, perfis e números.

✈️ O projeto

API REST completa para gestão de aeroporto regional. Cobre autenticação, CRUDs administrativos, operações do usuário autenticado, fluxos de estado do domínio, integração externa, upload de arquivos e regras de negócio reais.

Desenvolvido como avaliação técnica backend em 5 dias, seguindo o enunciado AV-05-AEROPORTO.

📚 Stack técnica

Framework NestJS + TypeScript
Banco PostgreSQL
ORM Prisma 7 + driver adapter (@prisma/adapter-pg) + migrations
Validação DTOs + class-validator + ValidationPipe
Autenticação JWT + bcrypt + 3 guards (API Key, JWT, Roles)
Integração externa HttpService + Open-Meteo (clima e geocoding)
Upload Multer + validação de tipo e tamanho
Segurança Helmet + Compression + Rate Limiting + X-API-KEY
Documentação Swagger em /api/docs
Configuração .env + ConfigService + validação com Joi

🗂️ Entidades modeladas (7 obrigatórias do enunciado)

🩺 Health Check — GET /health EXTRA

O que é: endpoint de observabilidade que responde "a API está viva e saudável?". É o sinal vital do sistema.

O que verifica (em paralelo):

  • A API está rodando
  • O banco responde (SELECT 1 no Postgres)
  • A API externa de clima responde (chamada leve)

Como acessar: GET /health — só precisa do X-API-KEY. 

{
  "status": "ok",
  "uptimeSegundos": 1234,
  "servicos": {
    "database": { "status": "ok" },
    "climaApi": { "status": "ok" }
  }
}

Pra que serve: ferramentas de monitoramento (Kubernetes, AWS) batem nesse endpoint periodicamente. Se algo falhar, elas reinicia a instância sozinhas — sem ninguém acordar de madrugada.

🎤 O que falar se perguntarem:

"O /health é o endpoint de observabilidade. Reporta o estado dos serviços críticos — banco, APIs externas e uptime. Ferramentas de monitoramento batem nele e decidem se a instância está saudável. Não faz regra de negócio, só observa."

📊 Dashboard — GET /dashboard/indicadores EXTRA

O que é: endpoint que agrega dados e devolve visão de negócio pronta. É o "painel do gerente".

Indicadores calculados em tempo real:

voosPorStatus Quantos voos em cada status
taxaOcupacaoMedia % média de ocupação das aeronaves
portaoMaisUsado Portão com mais voos + quantidade
embarquesUltimas24h Embarques realizados nas últimas 24h
companhiaComMaisReservas Companhia líder + total

Como acessar: GET /dashboard/indicadores — exige X-API-KEY + Bearer + role OPERATOR ou ADMIN.

Pra que serve: ferramenta de decisão. O gerente do aeroporto olha e enxerga "portão A1 está sempre cheio" → precisa de mais; "companhia X = 60% das reservas" → parceria estratégica.

🎤 O que falar se perguntarem:

"O dashboard agrega indicadores em tempo real. Não foi pedido no enunciado, mas demonstra que eu pensei além da API técnica, no valor que ela entrega ao negócio."

Endpoint Analogia Responde

  • Swagger aberto: http://localhost:3000/api/docs
  • Banco populado: npx prisma db seed (se precisar)

Bloco 1 — Mostrar que a API é protegida 🔥

Endpoint: GET /health sem auth.

  1. Se já tiver autorizado, clica em Authorize → Logout.
  2. Vai em GET /health → Try it out → Execute.
  3. Resultado: 401 "X-API-KEY inválida ou ausente".

O que falar:

"Toda a API é protegida por uma chave. Vou mostrar o que acontece sem ela antes de autenticar."

Bloco 2 — Autenticar e ver o Health OK 🔥

  1. Authorize → cola aeroporto-api-key-2026-segura no X-API-KEY → Authorize.
  2. Faz login via Postman (POST /auth/login com {"email":"admin@aeroporto.com","senha":"Admin@123"}) e copia o token.
  3. Cola o token no campo Bearer Token → Authorize → Close.
  4. Refaz GET /health → 200 com database: ok e climaApi: ok.

O que falar:

"Duas camadas: X-API-KEY pra identificar a aplicação, Bearer pra identificar o usuário. O /health reporta o estado do banco e da API externa."

Bloco 3 — Listagens com filtros e paginação 🔥

Endpoint: GET /voos

  1. GET /voos sem filtros → 8 voos, ordenados por data.
  2. GET /voos?status=EMBARCANDO → só 1 (voo 6, G3202).
  3. GET /voos?status=PROGRAMADO&limit=3 → 3 voos + meta.totalPages: 3.

O que falar:

"Todas as listagens são paginadas com filtros e ordenação. O meta traz total, página atual e total de páginas."

Bloco 4 — Fluxo do PASSENGER 🔥

Login: passageiro@aeroporto.com / Passageiro@123

  1. Login via Postman → copia token → Authorize no Swagger.
  2. Criar reserva no voo 5 (G3201, CGH→BSB) com assento livre: 
    POST /reservas
{ "vooId": 5, "assento": "30A" }
    → 201 com reserva criada.
  3. GET /reservas/minhas → lista só as reservas desse passageiro.

O que falar:

"A identidade vem do JWT — nunca do body. Ninguém consegue reservar em nome de outro."

Bloco 5 — Regras de negócio em ação 🔥

  1. Assento já ocupado: POST /reservas { "vooId": 1, "assento": "15B" } → 409 "Assento já ocupado neste voo".
  2. Transição de estado inválida (como OPERATOR): PATCH /voos/3/status { "status": "DECOLADO" } → 400 "Transição de PROGRAMADO para DECOLADO não é permitida".
  3. Cancelar voo com reservas ativas (OPERATOR): PATCH /voos/1/status { "status": "CANCELADO" } → 409 "existem 6 reservas ativas".

O que falar:

"As 4 regras obrigatórias do enunciado estão todas implementadas e cada uma retorna o HTTP correto."

Bloco 6 — Autorização em ação 🔥

Token: PASSENGER (passageiro@aeroporto.com)

  1. PASSENGER criando voo (rota só de OPERATOR/ADMIN):
    POST /voos com body { "numero": "HACK1", "origem": "GRU", "destino": "GIG", "dataPartida": "2027-01-01T10:00:00Z", "dataChegada": "2027-01-01T12:00:00Z", "aeronaveId": 1, "portaoId": 1 }
    → 403 "Acesso negado. Necessário: OPERATOR, ADMIN"
  2. PASSENGER listando usuários (rota só de ADMIN):
    GET /usuarios
    → 403 "Acesso negado. Necessário: ADMIN"
  3. PASSENGER vendo reserva de outro (rota autenticada, mas é de terceiro):
    GET /reservas/1 (com o /1 no final! — reserva da Maria)
    → 403 "Você não tem permissão para acessar esta reserva"
    ⚠️ As duas mensagens de 403 são diferentes: uma vem do RolesGuard (role errado), outra do service (recurso de terceiro).

Bloco 7 — Embarque (voo 6 = EMBARCANDO) 🔥

Login: operador@aeroporto.com / Operador@123

  1. POST /embarques { "reservaId": 21, "observacao": "Embarque normal" } → 201.
    Reserva 21 = passageiro@aeroporto.com, assento 1A, voo 6 (G3202 EMBARCANDO).
  2. Embarque duplicado: repetir a chamada → 409 "Esta reserva já foi embarcada".
  3. Voo não está EMBARCANDO: POST /embarques com reserva do voo 1 → 400 "Voo precisa estar EMBARCANDO".

Bloco 8 — Integração externa ⭐

  1. GET /voos/3/clima → 200 com clima de Recife (VCP → REC).
  2. GET /voos/2/clima → 200 com clima de Porto Alegre (GIG → POA).
  3. Comentar que erros são tratados: 503 se API cair, 504 em timeout.

O que falar:

"Uso HttpService pra consultar a Open-Meteo: geocoding + clima. Timeout configurável por env, siglas IATA traduzidas pra nome de cidade."

Bloco 9 — Extras que impressionam ⭐

  1. GET /dashboard/indicadores (OPERATOR) → métricas agregadas: 8 voos por status, portão mais usado, companhia líder.
  2. Mencionar rate limiting no login (5/min) sem precisar executar.

O que falar:

3. Regras de Negócio Obrigatório

As 4 regras obrigatórias do enunciado + extras implementadas. Cada card mostra onde, o que faz, e como testar.

📌 Regra 1 — Capacidade da aeronave OBRIGATÓRIA

O que é: um voo não pode ter mais reservas ativas do que a capacidade da aeronave.

Onde está: reservas.service.ts — método criar.

Como implementei: contagem de reservas ativas + criação envolvidas numa transação com isolamento Serializable. Isso evita race condition — duas requisições simultâneas não passam juntas.

Se testarem: 409 "Aeronave sem assentos disponíveis para este voo".

O que falar se perguntarem:

"A regra mais delicada. Se eu só contasse e depois criasse, duas requisições simultâneas no último assento passariam. Por isso uso transação Serializable — o Postgres serializa as operações e aborta uma das duas."

📌 Regra 2 — Conflito de portão OBRIGATÓRIA

O que é: dois voos não podem usar o mesmo portão no mesmo intervalo de tempo.

Onde está: voos.service.ts — método existeConflitoPortao.

Como implementei: detecção de sobreposição de intervalos com a fórmula inicio_A < fim_B AND inicio_B < fim_A. Voos cancelados são ignorados (não ocupam portão). Na edição, o próprio voo é excluído da checagem.

Se testarem: 409 "Este portão já está ocupado por outro voo neste intervalo".

O que falar se perguntarem:

"Uso lógica de interseção de intervalos. Dois intervalos [a1,a2] e [b1,b2] se sobrepõem se a1 < b2 e b1 < a2. Uso essa regra no filtro do Prisma."

📌 Regra 3 — Embarque único OBRIGATÓRIA

O que é: uma reserva só pode ser embarcada uma vez.

Onde está: embarques.service.ts + @@unique(reservaId) no schema.

Como implementei: dupla proteção — constraint no banco + checagem no service. A constraint garante integridade mesmo em corrida; a checagem no service dá mensagem amigável em vez de erro P2002 genérico.

Se testarem: repetir o POST de embarque na mesma reserva → 409 "Esta reserva já foi embarcada".

O que falar se perguntarem:

"Fiz defesa em profundidade: constraint no banco garante que nunca duplica, e a checagem no service dá uma mensagem específica ao invés de cair no erro P2002 genérico do Prisma."

📌 Regra 4 — Voo cancelado não permite embarque OBRIGATÓRIA

O que é: se o voo foi cancelado, ninguém pode embarcar nele.

Onde está: embarques.service.ts — método criar.

Como implementei: antes de criar o embarque, verifico o status do voo. Se for CANCELADO, rejeito. Também exijo que o voo esteja em EMBARCANDO — se estiver em outro estado, rejeito com mensagem diferente.

Se testarem: 409 "Voo cancelado não permite embarque".

O que falar se perguntarem:

"Primeiro checo se o voo está cancelado (retorno 409 com mensagem exata do enunciado). Se não estiver cancelado, checo se está no estado EMBARCANDO — se não estiver, retorno 400."

⭐ Regra 5 — Assento único ativo por voo

O que é: não pode ter 2 reservas ativas no mesmo assento do mesmo voo. Mas se uma for cancelada, o assento libera.

Onde está: reservas.service.ts — checagem dentro da transação.

Detalhe importante: essa regra foi refinada durante o desenvolvimento. Antes, a constraint do banco travava o assento pra sempre. Descobri que uma reserva cancelada impedia nova reserva do mesmo assento. Corrigi movendo a validação pro service, filtrando só reservas não-canceladas.

O que falar se perguntarem:

"Percebi durante os testes que cancelar uma reserva não liberava o assento. Removi a constraint de unicidade do banco e movi a validação pro service, checando apenas reservas ativas. Assim o histórico de canceladas é preservado, mas o assento volta a ficar disponível."

⭐ Regra 6 — Cancelar voo exige zero reservas ativas

O que é: não dá pra cancelar um voo que tem passageiros com reserva ativa. O operador precisa resolver as reservas antes.

Onde está: voos.service.ts — método atualizarStatus.

Se testarem: 409 "Não é possível cancelar o voo: existem N reserva(s) ativa(s)".

⭐ Regra 7 — Voo não pode ter data no passado

O que é: bloquear criação de voos com dataPartida retroativa.

Onde está: voos.service.ts — método criar.

Se testarem: 400 "Data de partida não pode ser no passado".

⭐ Regra 8 — Transições de status validadas

O que é: cada entidade tem um fluxo de estados válido. Transições fora do fluxo são rejeitadas.

Fluxos implementados: 

Voo:      PROGRAMADO → EMBARCANDO → DECOLADO
          qualquer    → CANCELADO (exceto DECOLADO)

Reserva:  CONFIRMADA → UTILIZADA
          CONFIRMADA → CANCELADA

Embarque: PENDENTE | REALIZADO | BLOQUEADO

Se testarem: 400 "Transição de X para Y não é permitida".

📊 Resumo — Regra → Erro → Código

5. Perguntas Prováveis Preparação

Perguntas que a banca pode fazer + respostas prontas. Ensaie em voz alta — não decore, entenda.

🏗️ Arquitetura

Por que você separou o projeto em módulos?

"Cada domínio tem seu próprio module, controller e service. Isso isola responsabilidades: o controller só cuida do HTTP, o service só cuida da regra de negócio, e o PrismaService centraliza o acesso ao banco. Fica fácil dar manutenção e testar."

Onde ficam as regras de negócio?

"Sempre no service. Os controllers só recebem a requisição, validam o formato via DTO e delegam. Nenhum controller tem if de regra de negócio."

Por que usar DTOs em vez de receber o objeto direto?

"O DTO define o contrato de entrada. Com class-validator + ValidationPipe global, tudo que chega é validado antes de tocar o service. Também evita que campos não autorizados passem — o forbidNonWhitelisted rejeita body com campo extra."

Se eu pedir pra adicionar uma nova entidade, o que você muda?

"Crio o model no schema.prisma, rodo a migration, crio a pasta do módulo com service, controller, DTOs, e registro no app.module. O padrão se repete."

🗄️ Prisma / Banco de Dados

Como você modelou os relacionamentos?

"Usei relations reais do Prisma, não FKs soltas. Companhia tem várias aeronaves, aeronave tem vários voos, voo tem várias reservas, e reserva tem um embarque. Isso permite usar include e _count pra trazer dados relacionados em uma única query."

Por que usar migrations e não db push?

"Migrations ficam versionadas no Git. Qualquer pessoa que clonar o projeto consegue rodar 'npx prisma migrate deploy' e ter o mesmo banco. É o padrão de produção."

O que é o driver adapter do Prisma 7?

"É uma mudança do Prisma 7 — em vez do client nativo compilado, ele usa o driver do banco diretamente. No nosso caso, o @prisma/adapter-pg. Isso deixa o bundle menor e a conexão mais previsível."

O seed apaga dados existentes?

"Não. Ele é idempotente — antes de criar, checa se o registro já existe. Posso rodar várias vezes sem duplicar nada."

📏 Regras de Negócio

Como você impede que 2 pessoas reservem o último assento ao mesmo tempo?

"Uso transação com isolamento Serializable. O Postgres serializa as duas operações — se duas rodarem juntas, uma delas é abortada e recebe P2034, que eu trato como 409 'tente novamente'. Sem isso, haveria race condition."

Como funciona a detecção de conflito de portão?

"Uso interseção de intervalos. Dois voos conflitam se a partida de um for antes da chegada do outro E vice-versa. Voos cancelados são ignorados, e na edição eu excluo o próprio voo da checagem."

Se o passageiro cancelar, o assento volta a ficar disponível?

"Sim. Durante os testes eu percebi que a constraint de unicidade no banco não liberava o assento ao cancelar. Removi essa constraint e movi a checagem pro service, validando apenas reservas não-canceladas. Assim o histórico é preservado e o assento volta a ficar disponível."

Por que bloquear cancelamento de voo com reservas ativas?

"Pra proteger o passageiro. Se cancelasse direto, os clientes ficariam no prejuízo. A regra força o operador a resolver as reservas primeiro — cancelar ou realocar — antes de cancelar o voo."

🔐 Segurança

Por que usar X-API-KEY além do JWT?

"São camadas diferentes. O X-API-KEY identifica a aplicação cliente — só quem tem a chave consegue falar com a API. O JWT identifica o usuário. Isso evita que qualquer app externo consuma a API sem autorização prévia."

Como você protege contra usuário alterando ID no body?

"Os DTOs de reserva não têm campo usuarioId — o ID vem sempre do @CurrentUser, extraído do JWT. Mesmo se mandarem no body, o forbidNonWhitelisted rejeita com 400. E o service checa se o recurso pertence ao usuário autenticado antes de qualquer ação."

As senhas ficam salvas como?

"Hasheadas com bcrypt, custo 10. Em nenhum endpoint a senha ou o hash é retornado — sempre faço select explícito dos campos ou monto o objeto sem a senha."

Por que o Helmet e o Compression?

"O Helmet adiciona headers HTTP de segurança — proteção contra XSS, clickjacking, sniffing. O Compression reduz o payload das respostas maiores que 1KB. Ambos são uma linha no main.ts e são boas práticas."

Como funciona o rate limiting?

"Uso @nestjs/throttler global: 100 requisições por minuto por IP. No /auth/login, aperto pra 5 por minuto contra brute force. Se estourar, retorna 429."

⚠️ Tratamento de Erro

Como você escolhe o status HTTP correto?

"400 pra body inválido ou operação incompatível com o estado atual. 401 pra ausência de autenticação. 403 pra autenticado sem permissão. 404 pra recurso inexistente. 409 pra conflito de regra de negócio. Essa separação é importante — o cliente sabe se o problema é dele, do servidor, ou da regra."

Por que a mensagem do erro é específica e não genérica?

"Pra dar contexto. 'Conflito ao criar reserva' não diz nada. 'Assento já ocupado neste voo' é acionável. Descobri que o Prisma 7 com driver adapter mudou o formato do erro P2002 e ajustei o handler pra ler o formato novo."

🎯 Perguntas Difíceis (as que dão medo)

Se eu duplicar a API em 2 servidores, a regra de capacidade funciona?

"Funciona porque a garantia está no banco, não na aplicação. A transação Serializable é do PostgreSQL — mesmo com 2 servidores, o banco serializa as escritas. Se fosse um lock em memória, aí quebraria."

Você testou o upload com arquivo gigante?

"Sim — configurei limite de 5MB via ParseFilePipe. Acima disso, retorna 400 com mensagem clara. Os tipos permitidos também são validados por mimetype."

Se a API de clima cair, o que acontece?

"A rota do clima retorna 503 'API externa indisponível'. Configurei timeout de 5s — se estourar, retorna 504. O resto da API continua funcionando normal, porque a integração é isolada num endpoint só."

Por que você não usou DELETE nos recursos administrativos?

"Prefiro inativar a deletar. Isso preserva o histórico — reservas antigas ainda apontam pra companhias e aeronaves que existiram. Se eu deletasse, quebraria as FKs e perderia dados. É o padrão de soft delete."

O que você faria diferente se tivesse mais tempo?

"Adicionaria testes automatizados com Jest, versionaria a API em /v1, e colocaria um refresh token no lugar do JWT de 8h. Também consideraria um cache Redis para os indicadores do dashboard."

6. Decisões Técnicas Profundidade

Cada decisão tem o que foi feito, o porquê e o que foi descartado. Se te perguntarem algo profundo, a resposta está aqui.

🔒 Transação Serializable na criação de reserva

O que foi feito: a checagem de capacidade + criação da reserva rodam dentro de uma transação com isolationLevel: 'Serializable'.

Por quê: sem isso, duas requisições simultâneas no último assento passariam as duas na checagem e ambas criariam reserva — estourando a capacidade. Com Serializable, o Postgres serializa as transações e aborta uma.

Alternativa descartada: usar ReadCommitted + lock manual. Mais complexo e menos seguro.

Trade-off:

Serializable pode gerar conflito (P2034) em alta concorrência. Trato isso retornando 409 com "tente novamente" — o cliente pode reenviar. É o preço da integridade.

🛡️ Guards em camadas (API Key → JWT → Roles)

O que foi feito: 3 guards aplicados em ordem:

  1. ApiKeyGuard — global, exige X-API-KEY em tudo
  2. JwtAuthGuard — nas rotas privadas, valida o token
  3. RolesGuard — checa se o role do usuário está autorizado

Por quê: defesa em profundidade. Cada camada responde uma pergunta diferente:

  • "Essa aplicação pode chamar a API?" → API Key
  • "Esse usuário está autenticado?" → JWT
  • "Esse usuário tem permissão?" → Roles

Efeito colateral bom: o ApiKeyGuard roda antes do ThrottlerGuard, então requisições com chave errada nem contam pro rate limit. Isso dificulta ataques de reconhecimento.

📝 Interceptor global só pra log (sem regra de negócio)

O que foi feito: um LoggingInterceptor global que registra método, rota, status HTTP e tempo de execução de cada requisição.

Por quê não colocar regra de negócio ali? O enunciado proíbe explicitamente. Interceptors rodam em toda requisição — colocar regra lá espalha lógica por todo lado. Regra vive no service. 

[HTTP] POST /reservas → 201 (54ms)
[HTTP] POST /reservas → 409 (55ms) - Você já possui reserva para este voo
[HTTP] POST /reservas → 400 (2ms) - Bad Request Exception

Valor prático: em produção, saber que uma rota demora 500ms é o primeiro passo pra otimizar. Sem interceptor, isso vira caça ao tesouro.

📋 DTOs com class-validator + ValidationPipe global

O que foi feito: toda entrada de dados passa por um DTO decorado com validadores. O ValidationPipe global está configurado com whitelist: true, forbidNonWhitelisted: true e transform: true.

Cada flag faz o quê:

  • whitelist → remove campos que não estão no DTO
  • forbidNonWhitelisted → em vez de só remover, rejeita com 400
  • transform → converte tipos (query string "1" → número 1)

Por quê: segurança e consistência. Sem forbidNonWhitelisted, alguém poderia mandar usuarioId no body de reserva — o DTO não tem esse campo, mas sem a flag o Prisma poderia usar o valor. Com a flag, é rejeitado antes.

🗑️ Soft delete em vez de DELETE físico

O que foi feito: entidades administrativas (Companhia, Aeronave, Portão, Usuário) têm campo ativo. A rota /desativar só muda o booleano. Não há DELETE.

Por quê: integridade histórica. Uma reserva antiga ainda aponta pra uma aeronave que existiu — se eu deletasse, a reserva quebraria ou ficaria órfã. Sem contar que auditoria exige histórico.

Regras que eu adicionei:

  • Não dá pra desativar Companhia com voos ativos
  • Não dá pra desativar Aeronave com voos ativos
  • Não dá pra desativar Portão com voos ativos
  • Usuário não pode desativar a si mesmo
  • Usuário inativo não faz login (403)

🐛 Tratamento específico do erro P2002 (Prisma 7)

Problema: quando 2 reservas tentam violar a constraint de unicidade (usuário duplicado no voo), o Prisma 7 + driver adapter do Postgres retorna o erro P2002 num formato diferente do Prisma "clássico".

O que descobri: em vez de error.meta.target (array), ele retorna error.meta.driverAdapterError.cause.constraint.index (string) — ex: reservas_usuarioId_vooId_key.

Como resolvi: o handler tenta os dois formatos — o novo primeiro, o antigo como fallback. Depois busca "usuarioId" dentro do nome da constraint pra decidir a mensagem.

Como descobri:

Adicionei um console.log temporário dentro do catch pra ver o formato real do error.meta. Vi que não era array, era aninhado. Ajustei o código pra ler de lá e removi o log depois.

📦 Health e Dashboard como módulos separados

O que foi feito: /health e /dashboard/indicadores são módulos próprios, não fazem parte de nenhum domínio.

Por quê: eles não pertencem a nenhum recurso específico. Colocar em voos/ seria semanticamente errado. Cada um cuida do seu escopo — o dashboard agrega dados de voos, reservas e embarques; o health checa infraestrutura.

Bônus: são endpoints que o enunciado não pediu. Foram implementados pra demonstrar senioridade — health é padrão de produção, dashboard mostra visão de negócio.

📄 Paginação padronizada em todas as listagens

O que foi feito: todo GET de listagem aceita ?page=&limit=&orderBy=&order= e retorna { data: [...], meta: { total, page, limit, totalPages } }.

Por quê o formato { data, meta }: separa conteúdo de metadados. Se você retorna um array puro, o cliente não sabe quantos registros existem no total, nem quantas páginas. Com meta, ele pode montar a paginação.

Proteção contra SQL injection: o orderBy aceito é validado contra uma whitelist de colunas permitidas. Se passarem algo estranho, cai no default. Nunca interpolo strings direto.

Limite máximo: o limit é travado em 100 via @Max(100). Isso evita que alguém faça ?limit=999999 e derrube o banco.
